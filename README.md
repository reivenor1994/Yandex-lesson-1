# Задание 1

## Уровень 1 - Архитектурное решение
Используется **Webpack Module Federation** по следующим причинам:

1. Единый стек технологий (React): Приложение разработано на React, и нет необходимости использовать разные фреймворки (например, React, Vue, Angular)
2. Упрощённая настройка для React-проектов:  Webpack Module Federation требует минимальной настройки для работы с React-проектами
3. Эффективное совместное использование кода между командами: Главной нашей целью является загрузка части приложения (модули, компоненты) из разных сборок во время выполнения, чтобы разные команды
   могли делиться кодом между собой уменьшая дублирование и упрощая обновления.
4. Single SPA больше подходит для проектов, где используются разные фреймворки (например, React, Vue, Angular): В нашем случае, где весь проект написан на React, Single SPA добавляет излишнюю сложность,
   так как его основное преимущество — поддержка мультифреймворковости — не востребовано.

## Обоснование декомпозиции

1. **Разделение по функциональности**:
    - Специфичный функционал разбит по приложениям (аутентификация, профиль, контент)

2. **Повторное использование компонентов**:
    - Общие UI-элементы вынесены в shared-app

3. **Масштабируемость**:
    - Возможность подключения новых микрофронтендов без изменений host

4. **Безопасность**:
    - Изоляция чувствительной логики аутентификации
    - Защищённые маршруты в основном приложении

## Описание взаимодействий

### Сервис платежных операций
1. Инициировать оплату - пользователь передает необходимые данные(ID пользователя, ID заказа, сумма заказа) в "Сервис платежных операций" чтобы начать оплату заказа
2. Результат оплаты - "Сервис платежных операций" при успешной/неуспешной оплате возвращает пользователю его ID статус заказа и ID заказа
3. Инициировать платёж — "Сервис платежных операций" инициирует платёж, отправив необходимые данные (ID пользователя, ID заказа, сумма заказа) в платёжный сервис.
4. Предоставить статус платежа — платёжный сервис принял запрос на проведение оплаты, подтвердил возможность проведения платежа со счёта клиента, назначил идентификатор для этой транзакции и установил статус.
5. Подтверждение платежа — "Сервис платежных операций" уведомляет платёжный сервис о подтверждении операции, отправляя ID транзакции.
6. Запросить статус платежа — "Сервис платежных операций" отправляет запрос в платёжный сервис для получения текущего статуса обработки транзакции по ID.
7. Подтверждение отмены платежа (альтернативный сценарий) — платёжный сервис уведомляет систему об успешной отмене платежа, предоставляя статус отменённой транзакции.

### Сервис регистрации/аутентификации и управления профилем
9. Регистрация пользователя - пользователь регистрируется в системе передавая необходимые данные (имя, фамилия, email, номер телефона, адрес)
10. Подтверждение регистрации/авторизации - после успешной регистрации пользователь получает ID, ему назначается роль и выдается токен
11. Авторизация пользователя - пользователь передает пароль для авторизации в системе

### Сервис управления заказами
11. Создать заказ - пользователь создает заказ, передавая необходимые данные о заказе (название, описание, сумму)
12. Подтверждение создания/редактирования заказа - после успешного создания заказа сервис возвращает ID заказа и его статус
13. Поиск заказов пользователя - пользователь передает свой ID для поиска всех своих заказов
14. Информация о заказе/заказах пользователя - сервис передает пользователю найденные заказ/заказы (название, описание, сумму)
15. Поиск заказа пользователя - пользователь передает свой ID и ID заказа для получения о нем детальной информации
16. Нотификация об изменении состояния заказа - сервис уведомляет пользователя об изменении статуса заказа
17. Редактировать заказ - пользователь передает информацию которую надо обновить в заказе

### Сервис управления услугами/товарами
18. Добавить товар/услугу - пользователь добавляет товар или услугу передавая необходимые данные (название, описание)
19. Редактировать товар/услугу - пользователь может редактировать ранее созданный товар или услугу
20. Удалить товар/услугу - пользователь может удалить ранее созданный товар или услугу
21. Поиск/сортировка/фильтрация - поиск товаров или услуг других пользователей (по их наименованию или по ID для детальной информации)
22. Подтверждение создания/редактирования/удаления - при успешной операции пользователь получает ID товара или услуги
23. Результат поиска - при успешной операции пользователь получает данные о найденных товарах или услугах (название, описание)

### Сервис управления апелляциями
24. Создать апелляцию - пользователь создает апелляцию передавая её описание
25. Подтвердить создание апелляции - сервис подтверждает создание апелляции передавая пользователю её ID и текущий статус
26. Нотификация об изменении статуса апелляции - сервис уведомляет пользователя об изменении апелляции

### Сервис управления аукционами
27. Создать аукцион - пользователь для создания аукциона передает в сервис необходимые данные (наименование аукциона, его ставку) и выбирает торговую площадку
28. Подтвердить создание аукциона - сервис подтверждает создание аукциона передавая пользователю его ID, текущий статус и ID торговой площадки
29. Редактировать аукцион - пользователь может редактировать ранее созданный аукцион (менять ставку и торговую площадку)
30. Нотификация об изменении статуса аукциона - сервис уведомляет пользователя об изменении статуса аукциона (передает его ID, статус, наименование)

### Сервис захвата изменений данных
31, 32, 33, 34. Отслеживание изменений в БД - Debezium отслеживает изменения в бд микросервисов и отправляет их в kafka

### Сервис мониторинга
35. Публикация изменений - сервис сохраняет сообщения из kafka для сбора статистики

### Сервис техподдержки
36. Создать заявку - пользователь для создания заявки передает в сервис необходимые данные (описание заявки и свой ID)
